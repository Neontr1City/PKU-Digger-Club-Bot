## 首版范围

只做三个页面：

| 页面 | 内容 |
| --- | --- |
| 提名 `/nominate` | 昵称、两首歌的艺人／曲名和可选备注；链接统一由后台核对补充，提交后进入队列 |
| 投票 `/today` 与 `/rounds/日期` | 当天一至多组歌曲卡片、封面、网易云／Apple Music 按钮、投票；截止后展示结果 |
| 管理 `/admin` | 密码登录；校曲确认、查看队列、按日指定组数／暂停、预览文案与结果图 |

提名人无需注册。投票仅用浏览器标识避免误重复提交；不引入验证码、短信、微信授权、邀请码分发或复杂防刷。管理员仍需密码，不能让公开访客改队列或排期。

## 简单实现方案

一个服务端应用＋普通手机网页＋SQLite 文件＋每日定时入口。活动代码在同一个项目内，页面由服务端生成，少量 JavaScript 处理交互；不预建通用问卷编辑器、插件平台或前后端多服务架构。

首版使用 Python 3.12、Flask、SQLite 和 Pillow，依赖固定在 uv.lock；模板生成网页，少量脚本用于复制。若微信接入服务要求另有数据库或容器，作为独立依赖记录。

```text
自建提名页 → 按序队列 → 曲目核对／确认 → 每日投票
                                              ↓
                                  截止计票 → 结果图与文案
                                              ↓
                                        微信发送模块
```

曲目检索由提名后台任务完成并缓存，自动入队。保存发行证据，只有无法确定歌曲的项交管理员；不以纯手工录入替代原需求中的检索辅助，也不在每日切换时临时搜索全网。

## 第一步：跑通提名和投票

- 空数据库启动，提交提名自动记录顺序。
- 曲目自动补全就绪后，按队列生成指定日期的一至多组对决；无法确定的项才人工补充。
- 歌曲卡分开展示听歌与投票按钮；平台链接缺失时明确标记。
- 浏览器每组保存一个选择；草案默认截止前允许改票、未听组可以跳过，截止前不公开实时票数。
- 投票接口按服务器时间拒绝过期提交；相同请求重试不增加票数。

验收：用虚构昵称的单组／两组样例走通提交、确认、投票和截止。验证重复提交、不同组计票和管理员访问保护即可，不做大规模压力或长期稳定性测试。

## 第二步：每日活动与结果图片

- 默认一天一组，日期覆盖组数，支持暂停；无就绪提名不创建空投票。
- 冻结截止结果，按既有艺人→专辑／EP→曲名规则生成祝贺语。
- 用确定性程序生成 PNG，正确排版中文、变音符号与长曲名。
- 每日任务按「昨日结果图→祝贺→今日曲目和链接」生成发送内容。
- 草案默认平局并列、零票不选胜者；已确认北京时间 12:00 发布、次日 11:59 截止；不擅自开启真实群定时任务。

验收：票数与图片一致，单组／多组、同艺人／同专辑、平局／零票按规则处理；任务重复执行不重复消费提名。
