## 精简方向与内存判断

- 活动业务很轻：此前同次 `docker stats` 快照中 app 约 44 MiB、worker 约 38 MiB、Caddy 约 36 MiB；这是即时值而非峰值。新增内存主要由完整微信客户端及显示环境决定，不与每天发几条消息成正比。
- 不部署多账号面板、独立浏览器或完整桌面环境；只保留官方微信、虚拟显示及必要的界面操作组件。远程查看仅在扫码和排障时启用；虚拟显示在客户端运行时仍需保留。卸载未运行的浏览器只减少磁盘占用，不能算作常驻内存节省。
- [WechatOnCloud](https://github.com/Gloridust/WechatOnCloud)维护者给出的整实例数据为空闲约 0.6 GiB、活跃约 1–1.5 GiB、面板另约 0.12 GiB。其参考配置为 2 核／2 GiB；不能把含显示环境的数字当成微信单进程的最低要求，也不能直接套用到本项目。
- 2 GiB 是值得验证的候选，4 GiB 是有余量的候选；1 GiB 与网站共用的难点是现有约 321 MiB 可用内存，尚不能证明绝对跑不起来。应以最小环境下的启动、扫码、发送 PNG 的实际峰值为准。
- 现有磁盘 swap 可承接冷数据，但不是内存压缩，会增加延迟和磁盘操作；zram 才是内存压缩，以 CPU 换容量，压缩率依数据而定。两者都不能保证把任意客户端压进指定内存。若采用容器上限，需要同时限制内存与 swap，达到上限可能终止微信进程，并不能完全隔离宿主的磁盘／CPU 压力。[Docker 资源限制](https://docs.docker.com/engine/containers/resource_constraints/)
- 仅在中午启动微信可减少全天占用，但启动峰值不变，且重启后能否无需手机确认必须实测，暂不当成已解决方案。本次沿用既有 swap，未启用 zram 或限制现有网站业务；客户端启动结果见下节。

## 最小验证步骤

1. 按用户选择在现有主机创建独立容器，不新增机器。只使用官方客户端，不安装有未确认许可的第三方面板或协议程序；限制构建／运行资源并检查网站健康。
2. Ubuntu x64、虚拟显示、轻量窗口管理器和受认证保护的远程查看入口；微信以普通用户运行。只开放受保护的 HTTPS，不将 VNC／控制端口直接公开。登录状态保存在测试机私有目录，不输出到日志或 Git。
3. 安装固定版本官方包，启动到登录界面，实测内存与界面可操作性；若不能启动或被要求使用其他环境，记录原始错误再讨论，不直接替换成修改过的客户端。
4. 用户在明确属于自己测试机的页面扫码。核对账号及准确群名，确认不是搜索出的同名联系人或另一群。界面自动化未必能提供稳定群 ID，不能在没有证据时声称已经绑定唯一 ID；无法唯一确认目标就不发送。
5. 先查看无障碍控件能否准确获取群标题和输入区域，再决定使用控件或固定布局界面识别。先验证一条指定测试文字，再测试 PNG 显示和现有投票链接。每一步单独确认，不接入每日定时任务。
6. 记录实际发送效果、内存、重启后登录状态、重新扫码需求；一次样例成功不等于长期稳定性承诺。不确定是否发送成功时停止，不盲目重试。
7. 验证通过后才实现正式发送适配器、发送进度持久化及离线邮件提醒，并另行确定常驻位置。失败也按期清理测试资源；网站和提名队列维持现状。

## 线程上限诊断证据（2026-09-28）

- GDB 捕获 `mars::stn` 线程 SIGSEGV，栈顶为 glibc `pthread_detach`。其余应用帧无符号，不能从这些地址推断全部内部逻辑。
- 宿主内核日志在 UTC 03:34:49、03:44:02、03:57:09 分别记录三个微信容器的 `fork rejected by pids controller`；对应三次登录后失败，配置均为 `pids_limit: 256`。这是实际线程创建被拒的证据，不是内存不足推测。GDB 累计创建线程记录 262 条，仅为累计值，不当作同时线程数。
- `pids_limit` 同时限制进程和线程；本项目设置的 256 限制过紧。调至 1024，继续保留 512 MiB 内存／1024 MiB 总量与非 root 权限。退出脚本增加 pids.current／pids.peak（内核支持时）／pids.events 和 memory.events，只记录计数。
- 这是有证据的配置修正；修正后的登录和实际发送仍需验证，不将此前三次失败归咎于手机分身。
- 1024 上限配置与退出计数已部署并重建诊断容器，实际恢复至原账号登录窗口，网站 HTTP 200；重新发起登录，等待手机确认后验收。
