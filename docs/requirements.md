# 需求与活动规则

更新：2026-09-27。状态：用户原始需求已记录；标为「建议／待确认」的规则尚未获选定。

## 1. 使用场景与范围

- 服务微信群「今天你滚了吗（pku版）」，约 200 多人，北京大学地下摇滚／独立音乐社群，英文名 PKU Digger Club；项目名 PKU-Digger-Club-Bot。
- 第一项活动为「每日斗蛐蛐」：每组两首歌曲，各组独立决出胜者。
- 机器人以独立账号加入现有群聊，拥有独立昵称与头像；这是用户期望的群内形态，具体账号接入方式尚待验证。
- 日常定时任务与微信发送不依赖用户本地电脑开机；优先使用免费云资源。账号初次登录或失效后仍可由本人手机扫码。
- 首版不做闲聊 AI、音乐播放服务、群成员画像、多群运营、商业化、压力测试或高可用集群。
- 不依赖付费大模型：常规排期、计票、消息与结果图由确定性程序完成；曲目歧义交管理员处理。
- 「内容自动准备」与「消息自动进入微信群」是两项独立能力。用户已确认优先自动发送，遇到实质困难后才考虑人工转发；不能以生成文案代替完成自动发群目标。

群友无需注册，不做复杂防刷；不再集成问卷星或迁移旧数据。

## 2. 提名与队列

每份提名是不可拆分的一组：提名人姓名／昵称、歌曲 A、歌曲 B。来源为自建提名页，长期开放；用户已确认没有旧队列，从空数据库开始。

提名表单字段：

| 字段 | 要求 |
| --- | --- |
| 提名人昵称 | 必填，保留原样；仅清理首尾空白及 HTML 转义 |
| A／B 艺人名、曲名 | 分栏必填，避免靠连字符猜字段边界 |
| 专辑、年份、版本备注 | 选填；现场版、混音版、重录版须明确 |
| 提交序号、提交时间 | 服务器自动生成，用于排序 |

只收集活动需要的昵称、曲目和备注，不要求手机号、邮箱或真实身份。群友不填写听歌链接；公开提交忽略额外传入的平台链接字段，统一由后台自动查找与补全；无法确定歌曲时管理员补充。

所有 Remaster／Remastered（重制母带）版本默认可接受，不需要在展示曲名或版本说明中标注，也不要求两平台重制年份一致。现场、混音、重新录制等不同录音仍需区分；来源记录保留平台原始发行信息。

按 `(提交时间, 提名 ID)` 排序；时间一致时 ID 定先后。同一请求重试不重复入队，不开发跨人、跨设备提名去重系统。

**建议／待确认：**队首歌曲有歧义时暂停该组、提示管理员；只有管理员明确跳过后才取下一组，避免程序悄悄改变提名顺序。修改或撤回已经发布的提名不回写历史投票。

## 3. 每日排期

- 时区固定 `Asia/Shanghai`。
- 默认每天 1 组；管理员可按日期设置 `0`（暂停）或任意合理正整数（多组）。日期覆盖只影响指定日期。
- 已确认北京时间每日 12:00 发布，次日 11:59:00 截止；11:59 起不再接收投票，12:00 开始下一轮。每日发布仍按昨日结果、祝贺、今日投票的顺序。
- 同一天 N 组对应 N 道独立单选题，建议共用一个当天投票链接；每组选择 A 或 B，不把所有歌曲合成一道多选题。
- 群友无需注册，使用随机浏览器标识记录每组选择，防止日常误重复提交，不保证跨设备一人一票。草案默认允许跳过、截止前改票；未选不计票，改票覆盖原选择。
- 排队数量不足时只准备实际可用的组数并提醒管理员；没有提名时不发布空投票。
- 一组只排入一次正式活动；生成草稿、预览或失败重试不能把下一组提前消费掉。

## 4. 每日执行顺序

1. 对前一活动日的投票执行截止，确认最终票数；不能把读取失败当成零票。
2. 保存带日期、每组 ID、截止时间、票数的结果快照。
3. 输出前一日结果图；同日多组可纵向排列，过长时分页。
4. 发布结果图，再发送祝贺消息。
5. 发布当天歌曲与投票链接，标记当天各组已发布。

人工转发路线：交付按上述顺序排列的图片和文本，管理员发送后点选「已发送」。全自动路线：每个发送步骤记录完成状态，失败时从未完成步骤继续。首日没有上一日投票时直接发布今日内容；停办日期不虚构结果。因故漏发的旧结果应显示真实活动日期，由管理员决定补发。

已确认补充：Apple Music 优先提供国区已验证条目；日区／美区可用于核对汉字、假名与罗马音，名称对应须保留目录 ID 或艺人别名来源，不凭转写猜身份。

## 5. 消息格式

当天文本模板：

```text
今天的曲目：{艺人 A} - {曲名 A} vs {艺人 B} - {曲名 B} 来自 {提名人} /
{艺人 C} - {曲名 C} vs {艺人 D} - {曲名 D} 来自 {提名人}
投票链接：{当天实际发布的投票链接}
```

只有一组时没有结尾分隔斜线。艺人／曲名来自核对记录，保留官方大小写、变音符号与标点。昵称不自动「纠错」；例如示例中的 `示例听众&#x20;` 只解码并清理为 `示例听众`。

祝贺语：`让我们恭喜{胜者称呼 1}（多组时用“和”连接其他胜者）👏🏻`。实际输出不带这里说明性的括号。

对**每一组的双方**计算称呼，不跨组比较艺人：

1. 艺人身份不同：使用胜者艺人正式署名。
2. 艺人身份相同，双方已确认的专辑／EP 不同且均可识别：使用胜者所属专辑／EP 名称。
3. 双方专辑／EP 相同、缺失或无法区分：使用胜者曲名。

艺人是否相同按已确认身份判断，不按大小写或别名字符串硬比较；合作艺人的 credit 按实际发行保留。多组胜者称呼重复时，建议保留组号与歌曲信息以免混淆，最终文案规则待确认。

## 6. 结果图与特殊结果

结果图至少显示：活动日期、每组两首「艺人 - 曲名」、各自整数票数、胜负／平局状态；建议增加提名人和截止时间。百分比以**该组有效选择总数**为分母，不使用整份问卷提交人数。封面是可选装饰，不能因封面缺失阻断准确计票。

**建议／待确认：**

- 正票数平局：图上标记平局，消息为「今天这组平局，双方都很能打👏🏻」，不随机选胜者。
- 双方零票：标记「本组暂无有效投票」，不发祝贺。
- 多组有胜者也有平局：祝贺明确胜者，再补充平局组；零票组单独说明。
- 提名为同一首同一录音：发布前提醒管理员处理，不自动创建无意义的对决。
- **已确认**：找不到一个平台的歌曲，保留可信平台链接，缺失项显示「暂未找到」，自动接受且不通知管理员；不能编造歌曲 ID。

## 7. 管理员能力

新提名默认自动纠错、检索、选择发行与封面并入队，规则见 [自动提名处理标准](nomination-pipeline.md)。只有无法确定的项需要管理员；单平台或封面缺失不需要放行。
后台首页提供“正在进行的投票”：按真实开始／截止时间列出所有进行中的轮次，包括跨日仍开放的活动。各组显示双方票数、得票比例、总票数、领先／持平／零票状态及截止时间；管理员可手动刷新，页面可见时每 15 秒局部更新。刷新不清空其他表单，失败时说明数据未更新，登录过期后要求重新登录。截止前计票仅管理员可见。

首版使用一个密码保护的管理页面：查看提名队列、确认纠错与版本、调整某天组数、暂停日期、明确跳过／恢复某组、预览消息、查看票数、重新生成结果图。管理员按需访问，无需先打通群内命令或开发多管理员权限体系。

若以后增加群内管理命令，需要可核验的管理员账号 ID；不能仅凭群昵称授予权限。

## 8. 最小数据模型（设计草案）

| 实体 | 保存内容 |
| --- | --- |
| nomination | 本地 ID、提交时间、昵称、原始输入、两首曲目引用、待核对／就绪／已排期／已发布／跳过状态 |
| track | 原始与正式艺人／曲名、身份 ID、版本、专辑／EP、发行日期、各平台链接与地区、核对来源、核对时间 |
| artwork | 所属 release、封面来源、所选版本、使用依据、图片缺失状态 |
| daily_round | 活动日期、起止时间、组数、所含提名、站内日期链接、发布状态 |
| vote | 活动组 ID、随机浏览器标识、选择、提交／修改时间；每组＋浏览器标识唯一 |
| result | 每组双方最终票数、截止时间、来源、胜负判定、结果图路径 |
| delivery | 当天结果图／祝贺语／新投票三个步骤的待发送／已确认状态 |

这些是逻辑实体，可在一个 SQLite 文件中按实际实现合并；不需要拆成多个服务。
