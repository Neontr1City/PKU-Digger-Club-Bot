# 小规模鲁棒性验证与故障预案

日期：2026-09-28。用户已确认测试群两轮完整流程成功，并要求验证约 200 多人社群的访问量和常见异常。本文不把本机测试等同于云端，也不把服务器处理时间当成手机端首屏时间。

## 范围和通过标准

使用 `deploy/check_small_group.py`：自行生成临时 SQLite、合成昵称／曲目与缓存封面；启动与生产相同的 Gunicorn **1 进程／4 线程**。不接收任意目标 URL 或生产数据库参数。仅回环 HTTP，禁用提名处理 worker、微信、SMTP；没有向在线曲库发出批量请求。

- 200 个独立 Cookie 会话，20 并发：打开投票页、两张封面、CSS、投票；其中 20 个重复提交。
- 200 次短时读取，50 并发。
- 20 份提名，10 并发，各重复提交一次。
- 12 次结果 PNG 请求，4 并发。
- 重启隔离网页服务，核对已有票数；截止后尝试投票，确认票数和冻结快照不变。
- SQLite 一致性备份后核对完整性和票数；非法 CSRF 返回 400、超大提交返回 413。

共 1,297 次逻辑 HTTP 操作，投票提交包含 303 后的页面跳转。测试最终必须恰好 200 票、20 份新增提名、无意外 HTTP 错误、无 Gunicorn 超时及数据库损坏。缓存封面是纯色合成图，**没有验证真实封面大小的公网传输速度**。不是 200 人持续高频刷新，也没有持续监控／长时压测。

原 Azure VM 上测试时使用单独临时容器，限制 **1 CPU、192 MiB 内存、256 MiB 含 swap、128 线程／进程**，禁用外网，仅挂载测试输出目录；生产数据库、登录状态和密钥均不挂载。每个阶段前若宿主可用内存不足 96 MiB 则停止后续阶段。任务结束移除容器。

在上述短时使用量内通过验收，不等于 200 人同时持续刷新或公网端到端延迟承诺。无需基于早期错误的发生器测量扩容。

以下保留本轮诊断过程，失败尝试不作容量结论：

- 本地原版本：1,297 操作通过；200 会话准确保留 200 票，20 份提名无重复。136 项原回归测试通过。
- 封面故障注入：同一 URL 模拟失败，原版本 16 次访问产生 16 次外部尝试；修正后并发同图只尝试一次，60 秒内不重复，冷却结束后能重新获取并缓存。最多两个同时发生的外部封面下载，不占满网页的四个请求线程。其他请求先返回占位，缓存命中不受限制。
- 修复后的 144 项回归测试通过，包括微信异常不盲重发、心跳告警去重、邮件失败退避、曲库有限重试与中断任务恢复。故障注入只在本地样本中实施，没有故意让真实微信掉线或填满服务器磁盘。
- 云端隔离容器首次启动：Docker 管理接口访问 containerd 超时，测试未开始；同次检查网站 `/health` 正常，app／worker／微信仍运行。没有把这一尝试计为应用并发测试通过，也没有为此重启 Docker 或微信。

- 云端第二次隔离尝试：200 会话完整访问／投票耗时 30.186 秒，200 次 50 并发读取耗时 35.155 秒；随后宿主可用内存低于 96 MiB，保护机制停止后续阶段。没有获得全套云端隔离通过结论；停止后可用内存回升到 300 MiB，网站健康正常。测试脚本随后补上进程退出超时的强制清理及失败报告保存。

## 轻量化改动

- 普通投票页无到期活动时不申请 SQLite 写锁；真正结算仍在事务内重新读取并冻结票数。新增持有写锁时仍可读取进行中投票的测试。
- 网页封面派生为 480×480、quality 82 的 WebP，生成一次后直接发送文件；600×600 原始缓存继续用于制图。源图改变会重新生成派生图，首次并发生成的其他请求可先取原 PNG，不等待转换。避免每个访客都用 Pillow 解码／缩放一次。
- 冻结结果按内容、渲染代码及封面版本缓存于 `OUTPUT_DIR/results/`，网页和微信共用。并发首次打开时一个进程只绘制一次，临时文件原子替换。缺图结果最多缓存 60 秒后再尝试；封面更新和设计源码改变使缓存失效。页面公开投票信息仍不缓存。
- 结果 PNG 输出从 1080 缩为 **864 像素宽**，保持原布局，使用 256 色快速量化和 PNG 压缩；保留 PNG，沿用微信的图片来源／指纹校验。冻结 PNG 支持浏览器缓存和 ETag，避免重复下载，不创建投票会话 Cookie。
- 两张含真实封面的既有本地多组样图分别由 1,190,809 → 224,586 字节、1,445,353 → 270,233 字节，约减少 **81%**；已目视检查文字／票数清晰。它们不是用户提到的 319 KB／145 KB 原文件，不据此声称那两张的精确新大小。不同封面压缩率不同。
- 优化后本地 1,297 操作再次全部通过；结果图请求中位数 63 → 5 ms、12 次合计 0.222 → 0.072 秒；50 并发页面读取 P95 81 → 73 ms。短测的微小变化可能有波动，不外推成云端提速倍数。

部署后第一次在线只读复验：含封面的 600 次操作出现 4 次失败，P95 3,049ms，最长观察到约 272 秒；纯页面 200 次／50 并发全部成功，P95 1,096ms。日志无应用异常／OOM，诊断发现明显内存及 IO 等待，网页其中一张原 PNG 679,703 字节。未将该次视作通过；随后追加网页 WebP 派生图及网站资源软保护。

随后定位测试生成器的额外开销：Python `urllib.request.build_opener` 默认构造 HTTPSHandler，并初始化证书环境，即使这里只请求本机 HTTP。早期脚本为每个请求／访客重复分配这部分资源，污染了同机小内存测试。只读脚本改用 HTTPConnection；隔离脚本使用仅含 HTTP 的 OpenerDirector，不再构造无用 TLS 上下文。修正后在线复验全部通过；不能把 272 秒异常等待解释为纯网站服务能力，也不能把前后差异全部归因于网站优化。

Compose 为 app／worker／Caddy 分别设置 96／64／32 MiB 的内存软保护，不是预先分配内存，不提高 VM 规格、不禁用 OOM。云端已核验 app 的 `memory.low=100663296`，三个容器配置数值正确；这是尽力而为的保护，不承诺绝不换页。保留微信既有 512 MiB 上限及登录会话，没有调整全局 swappiness。依据：[Docker 资源约束](https://docs.docker.com/engine/containers/resource_constraints/)、[Linux cgroup v2 memory.low](https://docs.kernel.org/admin-guide/cgroup-v2.html)（查证 2026-09-28）。

原始记录留在 Git 忽略目录 `output/robustness-20260928/`。单次短测不证明长期可用性、不同运营商网络速度或云主机 CPU 积分耗尽后的表现。

## 按症状处理

| 情况 | 当前行为 | 需要做什么 |
| --- | --- | --- |
| 群友集中点开、重复投票或重复点提交 | 投票按浏览器身份覆盖；同次提名 submission_id 去重 | 网络慢时先刷新确认，不反复新建提名；匿名机制不是防刷票系统 |
| 封面 CDN 超时／暂时不可用 | 有缓存直接用；缺图回退占位，60 秒后可再尝试，投票仍可提交 | 通常无需操作；恢复后再次打开页面即可重试 |
| Apple／网易云等曲库超时 | 原提名保留；后台隔 15 分钟重试，最多 3 次 | 耗尽后按邮件进入后台重新查找／核对；不要重复提交整组 |
| 排期时队首仍未解决／无新提名 | 不发空投票，不跳过队首；已准备的昨日结果可独立发送 | 核对或明确跳过队首；开启排期后，下次分钟任务可续排 |
| 微信退出或停留错误群聊 | 停止推送，持续故障邮件提醒 | 在管理页打开云端微信，手机分身确认登录，回到指定群并清空草稿 |
| 消息发送结果不确定 | 暂停，不自动重复发送 | 先在群里核对，再使用后台确认／重试；跨日消息按过期规则处理 |
| QQ SMTP 失败 | 保留待通知记录，按 15／30／60 分钟退避 | 核对 QQ 授权码及网络；整机停机／完全断网时同机邮件也不能即时发送 |
| 网站变慢／暂时打不开 | 当前同机服务有限资源，无自动扩容 | 先区分手机网络与服务器；检查健康、容器状态、内存／swap、磁盘和有限日志。先停止非必要测试，避免反复重启微信 |
| 部署时 Docker 管理接口超时 | 可能仍有网站和微信正常服务 | 先只读检查健康和在运行容器；等待后有限重试。不要据此清空登录目录或重启整个 Docker |
| 应用进程退出 | Compose `unless-stopped` 自动重启；SQLite 和文件队列持久化 | 检查恢复后的健康及后台状态；只在确认需要时重启 app／worker，不重建微信登录会话 |
| VM 停机／重启 | 恢复后容器启动，截止由实际时间判定，不延长投票 | 微信可能需要手机确认；当天未发内容可续发，跨日不补发旧“今天”消息 |
| 磁盘接近写满 | 无新存储服务或自动扩容；写入可能失败 | 查看占用，只清理确认无用的测试镜像、旧测试输出；先另存备份，不删除活动数据库和微信目录 |

网站排查在服务器项目目录内：

```sh
curl -fsS http://127.0.0.1:8000/health
docker compose --env-file .env.local -f deploy/compose.yaml --profile schedule ps
free -m
df -h /
docker compose --env-file .env.local -f deploy/compose.yaml logs --tail 30 app worker
```

日志可能含活动信息，留在私有目录，不贴公开仓库。当前无须增加 Redis、多实例、付费监控或扩容。

## 数据恢复

每日北京时间 12:10 的备份是同机备份。恢复步骤：

1. 暂停 app／worker 和微信发送进程，避免恢复过程中产生新的发送；保留当前 DB、outbox、配置及登录目录副本。
2. 选定备份，先在新文件上执行 SQLite `PRAGMA integrity_check`，核对轮次及票数；再替换正式数据库。当前尚未启用 WAL；若以后启用，须一并按 SQLite 正确方式处理附属文件。
3. 先以微信发送关闭状态启动网站，核对页面、截止时间和提名队列。
4. 群里已发消息无法回滚；将恢复库里的发送进度与现有收据／实际群消息核对后再恢复自动发送，不能直接删除收据重发。
5. 保存当前管理员密钥与 Cookie 签名密钥；随意换 SECRET_KEY 会改变浏览器投票身份和管理员会话。

同机备份无法应对整块磁盘丢失，正式运行后应定期另存一份到个人设备。本轮仅验证隔离库备份完整性与持久化，没有覆盖线上数据做恢复演练。

## 复跑

```sh
uv run python deploy/check_small_group.py --report output/small-group-check.json
uv run pytest -q
```

负载脚本只用标准库和已安装的项目依赖，不需要付费测试服务。结果输出包括每类操作的请求数、中位数、P95、最大耗时和异常状态数；P95 表示 95% 的这类操作在该时间内完成。
